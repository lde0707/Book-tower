# 2D 모바일 중력 퍼즐 개발 명세서

기준일: 2026-10-23. 대상: 스마트폰용 독립 퍼즐 게임을 구현하는 기획자와 개발자.

**상하좌우 중력 방향을 선택해 모든 블록을 함께 움직이고, 각 블록을 대응하는 목적지에 동시에 놓는 2D 모바일 퍼즐**을 만든다. 플레이어는 벽과 통로를 읽고 블록의 정지 위치와 방향 전환 순서를 계획한다.

이 문서는 기존 3D 방 기반 이식 문서를 대체한다. 모바일 기본안은 **세로 화면, 터치 버튼, 오프라인 플레이, 로컬 진행 저장**이다. Unity 2D를 기준으로 구현 책임을 설명하지만, 격자 계산과 데이터는 엔진에 독립적으로 유지한다. Android와 iOS에서 공통으로 적용할 설계이며, 실제 출시 플랫폼과 최소 지원 기기는 개발 시작 시 정한다.

동봉 데이터와 검사기는 기존 퍼즐에서 가져온 것이고, 화면·터치·저장·애니메이션 설계는 새 모바일 프로젝트에서 구현할 명세다. 완성된 모바일 앱이나 Unity 패키지가 포함된 것은 아니다.

## 1. 전달 파일과 초기 개발 범위

- [README.md](README.md): 2D 모바일 게임 규칙, UI, 데이터, 구현 구조, 저장과 검수 기준.
- [layouts.json](layouts.json): 기존 16개 퍼즐의 벽·블록·목적지·대표 해법 데이터.
- [verify_layouts.py](verify_layouts.py): 격자 이동 참조 구현과 데이터 검사기. Python 표준 라이브러리만 사용하며 게임 실행 파일은 아니다.
- [validation.txt](validation.txt): 동봉 16개 레벨의 대표 해법과 최단 방향 전환 수 검증 기록. 모바일 기기 테스트 결과는 아니다.

첫 구현 범위는 레벨 선택, 퍼즐 보드, 네 방향 입력, 되돌리기, 처음부터, 일시정지, 완료 화면, 로컬 저장이다. 3D 캐릭터 이동·방 탐색·점프·문 통과·관찰 카메라는 필요 없다. 광고·결제·계정·서버·일일 퍼즐은 초기 규칙 구현과 분리한다.

## 2. 핵심 플레이 규칙

### 보드와 블록

보드는 정사각형 셀로 이루어진 유한한 2D 격자다. 벽 셀과 보드 바깥으로는 이동할 수 없다. 블록은 회전하지 않는 정사각형이며, 현재 콘텐츠는 1×1과 2×2 크기를 사용한다. **size가 2인 블록은 총 4셀을 차지한다.**

각 블록에는 자기 목적지가 있다. 동일한 크기의 블록도 서로 다른 문양이나 번호로 구별하며, 다른 블록의 목적지에 대신 들어가면 해결되지 않는다. 목적지는 바닥 표시이며 장애물이나 블록 고정 장치가 아니다.

### 방향 명령

1. 위·아래·왼쪽·오른쪽 중 하나를 누른다.
2. 모든 블록이 같은 방향으로 동시에 움직이기 시작한다.
3. 각 블록은 벽·경계·다른 블록에 막히는 자신의 정지 위치까지 이동한다.
4. 먼저 멈춘 블록이 있어도 나머지는 계속 이동한다.
5. 모든 블록이 멈추면 다음 방향을 선택할 수 있다.

한 블록만 선택하거나 직접 끌어 옮기는 조작은 없다. 움직이는 도중 방향을 바꾸는 순발력 조작도 없다. 큰 블록과 작은 블록에 같은 이동 법칙을 적용한다. 한쪽 벽에 붙었거나 양쪽 벽 사이에 있다는 이유로 속도가 줄어들면 안 된다.

목적지에 도착한 블록도 다음 명령을 받으면 다시 움직인다. 모든 블록이 **자기 목적지에 동시에 놓이고 이동이 끝났을 때** 완료한다. 경로 중 목적지를 잠깐 지나가는 것은 완료가 아니다.

### 되돌리기와 처음부터

되돌리기는 직전 방향 명령 전의 모든 블록 위치, 중력 방향, 이동 횟수를 복원한다. 이동 중에도 사용할 수 있다. 기록이 비어 있으면 버튼을 비활성화한다.

처음부터는 초기 배치, 아래 방향, 이동 횟수 0, 빈 되돌리기 기록으로 복원한다. 모바일에서는 되돌리기와 떨어진 위치에 두고, 오조작을 줄이기 위해 확인창을 표시하는 기본안을 사용한다. 확인창을 연 동안 이동을 멈추고, 취소하면 이어서 진행한다.

이 명세에서는 원본과 동일하게 이동할 곳이 없는 방향 명령도 이동 횟수와 기록에 포함한다. 다만 모든 목표 위치가 시작 위치와 같다면 애니메이션 대기 없이 바로 조작 가능 상태로 돌아간다. 초기 배치부터 완료된 데이터는 제작 오류로 걸러낸다.

## 3. 스마트폰 화면 구성

### 세로 화면 기본 배치

상단에는 레벨 이름, 이동 횟수, 일시정지 버튼을 둔다. 중앙에는 보드 전체를 항상 보이게 표시한다. 하단에는 십자 형태의 네 방향 버튼과 별도의 되돌리기·처음부터 버튼을 둔다. 현재 중력 방향은 보드 가까이에 작은 화살표로 표시한다.

조작 버튼이 보드를 가리지 않아야 한다. 목표와 남은 블록 수를 보여 줄 수 있지만, 이동 중 잠깐 목적지를 통과한 상태를 완료로 표시하지 않는다. 완료 화면에는 다음 레벨, 다시 하기, 레벨 목록을 제공한다. 별점·제한 시간·최소 이동 수 공개는 기본 규칙에 포함하지 않는다.

핵심 플레이 화면은 카메라 이동, 핀치 확대, 보드 스크롤을 요구하지 않는다. 손가락으로 작은 블록을 직접 누르게 하지 않고 충분히 큰 방향 버튼으로 조작한다.

### 화면 크기 대응

노치·카메라 구멍·홈 제스처 영역을 제외한 안전 영역 안에 UI를 배치한다. 상단 정보와 하단 조작 영역을 확보한 나머지 영역을 보드 영역으로 사용한다. 벽을 포함한 전체 보드 크기가 들어가도록 셀 크기를 계산한다.

```text
cellPixels = min(boardAreaWidth / width, boardAreaHeight / height)
boardPixelWidth = width * cellPixels
boardPixelHeight = height * cellPixels
```

보드는 남는 영역의 중앙에 정렬한다. 가로와 세로를 따로 늘려 셀이 직사각형이 되지 않게 한다. F0·3C의 9×7과 나머지 13×11 보드 모두 화면에 맞아야 한다. 글자 크기가 커져 보드가 작아지더라도 조작 버튼을 겹치거나 잘라서는 안 된다.

방향·되돌리기 버튼의 터치 영역은 시각 아이콘보다 넓게 잡는다. 초기 설계값으로 약 48×48 이상의 논리 UI 단위를 출발점으로 사용할 수 있으나, 이는 플랫폼 인증 기준이나 물리적 크기 보장이 아니다. 선택한 Canvas 배율과 실제 휴대폰에서 한 손 조작을 확인해 확정한다. 보드 셀은 직접 누르는 버튼이 아니므로 같은 터치 크기를 강제하지 않는다.

출시 기본안은 세로 고정이다. 기기를 돌렸을 때 보드 상태나 진행 중 입력이 재초기화되지 않아야 한다. 가로 모드는 별도 레이아웃을 제작할 때 지원 범위에 추가한다.

## 4. 터치 입력 규칙

### 기본 조작

방향 버튼은 손가락을 눌렀다가 같은 버튼 안에서 뗐을 때 명령 한 번을 발생시킨다. 버튼 밖으로 이동해 손을 떼면 취소한다. 길게 누르기 자동 반복은 사용하지 않는다. 기기 흔들기나 기울이기를 중력 명령으로 사용하지 않는다.

첫 번째 유효 터치만 처리하고, 동시 터치로 명령이 중복되지 않게 한다. 방향 입력은 Ready에서 시작하고 Ready에서 끝난 터치만 수락한다. 이동 중 눌러 둔 손가락을 이동 종료 뒤 떼는 동작을 다음 명령으로 예약하지 않는다. 화면 전환·백그라운드 진입 시 진행 중 터치를 취소한다.

Moving에서는 방향 버튼을 비활성화하고 조작 가능 상태를 시각적으로 구분한다. 입력을 대기열에 쌓지 않는다. 되돌리기와 처음부터는 이동 중에도 사용할 수 있다. Paused와 완료 화면에서는 보드 방향 입력을 받지 않는다.

### 스와이프는 후속 선택 기능

첫 버전은 방향 버튼으로 규칙을 명확하게 전달한다. 스와이프를 추가한다면 보드 전체에 대한 방향 명령으로 처리한다. 개별 블록 드래그로 해석하지 않는다. 주축과 최소 이동 거리, 대각선 취소 조건을 정하고, 버튼과 스와이프가 같은 손동작으로 두 번 실행되지 않게 한다. 다른 메뉴에서 시작한 스와이프를 보드 입력으로 넘기지 않는다.

### 피드백과 접근성

수락한 방향은 버튼과 방향 표시기에 즉시 반영한다. 이동 종료와 퍼즐 완료의 피드백을 구별한다. 효과음·진동은 선택 설정이며, 꺼도 조작과 결과를 알 수 있어야 한다. 블록과 목적지는 색뿐 아니라 문양·번호로도 대응시킨다. 확대 텍스트와 연출 감소 설정이 상태 판정이나 정지 위치를 바꾸면 안 된다.

## 5. 2D 구현 구조

### 이동 결과를 격자로 결정

**Rigidbody2D의 마찰이나 충돌 해결기로 퍼즐 결과를 결정하지 않는다.** 정수 격자에서 정지 위치를 계산하고, SpriteRenderer 또는 UI 이미지가 그 결과까지 이동하는 구조를 기본 구현으로 삼는다. 중력은 게임 규칙의 방향 값이지 기기의 센서 값이나 Physics2D 전역 중력이 아니다.

이 구조는 기존 3D 런타임의 구현과 다르다. 원본은 Rigidbody 물리를 사용했고 벽 밀착 감속이 남아 있다. 모바일에서 Rigidbody를 Rigidbody2D로 이름만 바꿔 사용하는 것은 이 명세의 구현 방법이 아니다.

권장 책임 구분은 다음과 같다. 클래스 이름은 새 프로젝트에서 사용할 예시다.

- `PuzzleDefinition`: 보드, 벽, 블록 ID·크기·초기 위치·목표. 실행 중 불변 데이터.
- `PuzzleState`: 블록의 정수 위치, 방향, 이동 횟수, 완료 여부.
- `TiltSimulator`: 상태와 방향을 입력받아 정지 위치를 반환하는 순수 함수.
- `PuzzleController`: 명령 허용, 상태 전이, 되돌리기, 일시정지, 완료 이벤트.
- `BoardView`: 벽·목표·블록 스프라이트와 이동 표현. 정답 판정 권한은 없다.
- `TouchInputAdapter`: 터치를 방향·되돌리기·처음부터 명령으로 변환.
- `ProgressSaveService`: 안정된 상태, 레벨 진행, 설정을 로컬에 저장.
- `AppLifecycleAdapter`: 포커스·앱 활성 상태를 받아 입력 취소와 일시정지를 요청.

코어에 원본의 Room, GameFlow, PaperUI, 플레이어 컨트롤러, 문, 스토리 코드를 참조시키지 않는다. 화면, 효과음, 저장은 이동 시작·이동 종료·복원·완료 이벤트를 받아 동작한다.

### Unity 2D 표현 기본안

보드에는 고정 Orthographic 카메라와 SpriteRenderer를 쓰고, 버튼과 메뉴는 Canvas에 둔다. 보드를 Canvas 이미지로만 구성해도 같은 코어를 사용할 수 있다. 두 방식을 섞을 경우 좌표 변환은 BoardView 한 곳에서 처리한다.

렌더 순서는 배경, 목표 표시, 벽, 블록, 효과, UI로 명확히 정한다. 목표는 블록 뒤에서도 대응 문양을 읽을 수 있게 테두리를 남긴다. 블록의 그림자·종이 결·둥근 모서리는 시각 효과이며 점유 셀이나 이동 계산을 바꾸지 않는다.

퍼즐 계산에 Collider2D나 Rigidbody2D가 필요하지 않다. 선택적으로 터치 영역이나 장식 효과에 사용해도, 그 결과를 블록의 논리 위치나 승리 판정에 섞지 않는다. 프로젝트의 다른 Physics2D 물체가 보드를 밀거나 중력을 바꾸지 못하게 한다.

## 6. 동시 이동과 상태 관리

### 논리 이동

동봉 검사기의 `tilt`는 원본 배치 생성기의 격자 모델을 따른다. 블록 정체성은 배열 인덱스로 유지하고, 선택한 방향으로 앞쪽에 있는 블록부터 처리한다. 정렬 기준은 원본과 같은 `x*dx + y*dy` 내림차순이며 동률은 기존 인덱스 순서다. 다른 블록의 갱신된 위치도 장애물로 포함해 한 셀씩 이동 가능한지 검사하고 최종 위치를 구한다.

순수 함수 내부의 계산 순서와 화면에서 보이는 움직임을 혼동하지 않는다. 화면에서는 모든 블록이 동시에 출발한다. 현재 1×1·2×2 정사각형과 동봉 배치를 기준으로 이 순서를 유지한다. 회전 블록, 서로 다른 밀기 힘, 연결 블록 등 새 규칙을 추가한다면 이동 모델과 탐색기도 함께 수정한다.

### 벽과 무관한 이동 속도

한 방향 명령에 대해 모든 블록이 동일한 경과 시간과 이동 함수를 사용한다. 거리 단위를 셀로 통일하면 해상도와 보드 표시 크기가 바뀌어도 같은 속도로 느껴지게 만들 수 있다.

```text
L[i] = 시작 위치에서 계산된 정지 위치까지의 거리, 단위는 셀
commonDistance(t) = 0.5 * acceleration * t * t
travel[i](t) = min(L[i], commonDistance(t))
position[i](t) = start[i] + direction * travel[i](t)
```

`acceleration`은 셀/초² 단위의 게임 전체 공통 튜닝 값이다. 초기 프로토타입에서는 12로 시작해 가장 긴 경로의 체감 시간을 확인하고 조정할 수 있다. 기기 성능이나 옆면 접촉 수에 따라 값을 바꾸지 않는다.

한 블록이 멈춰도 공통 시간을 초기화하지 않는다. 이동 거리가 서로 다르다는 이유로 각 블록을 같은 완료 시간에 맞추지 않는다. 같은 시간에 같은 거리를 이동하다가, 자기 정지 위치에 도착한 블록만 멈춘다. 각 블록에 독립적인 정규화 easing을 적용해 서로 통과하는 표현도 피한다.

프레임마다 일정 거리씩 더하는 대신 경과 시간으로 위치를 계산한다. 프레임이 누락돼도 목표점을 넘지 않도록 clamp한다. 완료 시 시각 위치를 계산된 정지 위치에 정확히 맞춘다. 목적지로 임의 순간 이동시키는 방식은 사용하지 않는다.

### 상태 전이

```text
Ready + 방향 → 이전 상태 저장 → 정지 위치 계산 → Moving
Moving + 전체 표현 완료 → 논리 위치 확정 → Ready 또는 Solved
Ready/Moving + Undo → 표현 취소 → 명령 전 스냅샷 복원 → Ready
Ready/Moving + Reset 확정 → 표현 취소 → 초기 배치 복원 → Ready
Ready/Moving + Pause → 기존 단계와 시간을 기억 → Paused
Paused + Resume → 기존 단계 복원
Solved → 완료 화면 → 다음 레벨 또는 별도 다시 하기
```

스냅샷은 모든 블록 위치, 이전 방향, 이동 횟수를 포함한다. 이동 중에는 확정 상태와 대기 목표를 구분한다. 도착 표현이 끝나기 전에는 승리를 발생시키지 않는다. Undo·Reset·레벨 전환은 이동 세대 번호나 취소 토큰을 갱신해 오래된 완료 콜백이 현재 보드를 덮어쓰지 못하게 한다. 한 레벨 완료 이벤트는 한 번만 발생한다.

## 7. 앱 중단과 진행 저장

### 일시정지와 복귀

일시정지 메뉴, 앱 백그라운드 진입, 화면 잠금, 포커스 상실 시 새 입력을 막고 진행 중 터치를 취소한다. 이동 애니메이션의 시간도 멈춘다. 복귀할 때 실제로 지나간 벽시계 시간을 이동 시간에 더하지 않는다.

같은 프로세스로 돌아오면 멈춘 위치와 경과 시간을 유지한 채 일시정지 화면을 표시하고, 사용자가 계속하기를 누르면 재개한다. 원치 않는 복귀 직후 자동 이동과 터치 관통을 막는다. 시스템 뒤로 가기 입력을 제공하는 기기에서는 플레이 화면에서 일시정지 메뉴를 열고, 메뉴에서는 이전 화면으로 돌아가는 흐름으로 연결한다.

일시정지 원인이 겹치면 각각 관리한다. 처음부터 확인창을 닫았더라도 앱이 비활성 상태라면 이동을 재개하지 않는다. 앱이 돌아왔다는 이유로 사용자가 열어 둔 일시정지 메뉴를 자동으로 해제하지 않는다.

### 강제 종료 복구

종료 콜백에서만 저장하면 안 된다. 레벨 진입, 이동 확정, Undo·Reset 완료, 퍼즐 완료, 설정 변경 시 마지막 안정 상태를 저장한다. 저장 중 실패하면 직전 유효 저장을 유지하고, 임시 파일과 교체 방식 등으로 절반만 기록된 파일을 정상 저장으로 읽지 않게 한다.

이동 중 프로세스가 종료되면 **그 명령 직전의 확정 상태**를 복원하는 정책을 사용한다. 부분적인 소수 좌표를 저장해 벽 사이에 끼인 상태로 복원하지 않는다. 해당 명령 전 이동 횟수·방향·되돌리기 기록도 함께 복원한다. 이동이 완료되었다면 새 확정 상태를 저장한다. 앱이 메모리에 남아 있는 일시정지와 프로세스 재시작 복구는 구분한다.

저장 항목은 저장 형식 버전, 레벨 데이터 버전 또는 해시, 레벨 ID, 블록 ID별 정수 위치, 방향, 이동 횟수, 되돌리기 스택, 완료 레벨 목록, 효과음·진동·연출 설정이다. 입력 중인 손가락 ID나 애니메이션 오브젝트 참조는 저장하지 않는다.

로드 시 레벨 존재, 블록 ID·크기, 좌표 범위, 벽·블록 겹침을 다시 확인한다. 데이터 버전이 달라 현재 판을 복원할 수 없으면 해당 판만 초기화하고 유효한 완료 기록과 설정은 가능한 범위에서 유지한다. 잘못된 저장으로 앱이 시작되지 않는 상태를 만들지 않는다. 완료 기록은 레벨 ID 기준으로 중복 적용해도 같은 결과가 되도록 저장한다.

## 8. 레벨 데이터와 좌표

### JSON 계약

최상위 `layouts` 배열의 각 항목은 다음 필드를 가진다.

- `room`: 고유한 문자열 레벨 ID. 모바일에서 방 이름으로 보여 줄 필요는 없다.
- `family`: 0~4 유형 코드. 화면 테마나 물리 옵션이 아니다.
- `width`, `height`: 외곽 벽을 포함한 셀 수.
- `walls`: 각 벽 셀의 정수 `{x,y}` 배열.
- `cargo`: 각 블록의 `{x,y,size,gx,gy}` 배열.
- `route`: 검증용 방향 배열. 입력한 명령이 이 배열과 같은지 비교해 승리시키지 않는다.

`x,y`는 시작 위치, `gx,gy`는 목적지이며 둘 다 블록 영역의 좌하단 셀이다. `size=2`이면 `(x,y)`부터 `(x+1,y+1)`까지 차지한다. 현재는 cargo 배열 인덱스가 블록 ID이므로 임의 정렬하지 않는다. 새 저장 시스템에서는 명시적 ID를 부여하되 원본 인덱스와 대응을 고정한다.

```text
원점: 보드 왼쪽 아래. X는 오른쪽, Y는 위쪽으로 증가.
0 = 아래 (0,-1)
1 = 왼쪽 (-1,0)
2 = 위   (0,1)
3 = 오른쪽 (1,0)
```

스프라이트의 중심 좌표는 왼쪽 아래 보드 원점을 기준으로 다음처럼 계산한다. 목적지는 x,y 대신 gx,gy를 넣는다.

```text
centerX = (x + size/2) * cell
centerY = (y + size/2) * cell
```

이는 새 2D 보드의 좌표식이다. 원본 3D 생성기의 중앙 정렬 좌표식과 혼용하지 않는다. 화면 Y가 아래로 증가하는 UI에서는 표시 변환 한 곳에서만 Y를 뒤집는다. 격자 계산과 저장 좌표는 그대로 유지한다.

### 데이터 검사

정수 타입, 고유 ID, 크기 1 또는 2, 방향 값 0~3, 보드 범위를 검사한다. 시작 블록끼리, 목표 영역끼리, 각각과 벽이 겹치면 안 된다. 다른 블록의 시작 위치와 목표가 겹치는 것은 허용한다. 이동 과정에서 그 공간을 비울 수 있기 때문이다.

원본은 외곽 전체를 벽으로 막지만 새 이동 함수는 데이터의 외곽 벽 유무와 관계없이 보드 밖 이동을 금지한다. 잘못된 데이터에서 무한 이동이나 무한 탐색이 발생하지 않게 한다.

## 9. 콘텐츠 구성과 튜토리얼

동봉 데이터는 본편 15개와 선택 레벨 HD, 총 16개다. 모바일에서는 별도의 레벨 목록과 순서 설정으로 표시 이름을 바꿀 수 있으며, 기존 room ID는 저장과 테스트용으로 유지한다.

- **family 0:** F0·3C. 작은 블록 하나로 장애물 위쪽 우회를 익힌다. 각 3회 경로.
- **family 1:** 1A·2A. 작은 블록 하나로 여러 정지 위치를 연결한다. 각 5회.
- **family 2:** 1B·1D·2E. 작은 블록 둘을 동시에 조작한다. 각각 6·7·9회.
- **family 3:** 1C·2B·2D. 작은 블록 하나와 2×2 블록 하나가 다른 통로를 쓴다. 각각 7·8·9회.
- **family 4:** 1E·2C·2F·3A·3B·HD. 작은 블록 둘과 큰 블록 하나의 순서를 계획한다. 각각 8·9·8·10·11·12회.

숫자는 격자 모델의 최단 방향 명령 수이며 체감 난도나 플레이 시간이 아니다. 3C는 기본 규칙을 다시 사용하는 짧은 레벨이므로 순서대로 항상 어려워지는 구성은 아니다. 스마트폰용 튜토리얼의 이해도는 별도로 검증한다.

F0는 9×7 보드이고, 외곽 벽과 내부 `(4,1)`~`(4,4)` 수직 벽이 있다. 블록은 `(1,1)`에서 시작해 `(7,1)`로 간다.

```text
위(2): (1,1) → (1,5)
오른쪽(3): (1,5) → (7,5)
아래(0): (7,5) → (7,1), 완료
```

첫 화면에서는 블록과 같은 문양의 목적지를 보여 주고, 방향 버튼을 한 번 누르면 벽까지 이동한다는 규칙부터 가르친다. 이후 되돌리기를 소개한다. 복수 블록 레벨에서는 모두 함께 움직인다는 점과 도착한 블록도 다시 움직인다는 점을 강조한다. 힌트는 목표·정지 위치·다음에 볼 공간을 설명하는 단계로 구성하고, 터치 실수나 보이지 않는 정보로 난도를 만들지 않는다.

## 10. 2D 아트와 모바일 성능

한 화면에서 벽, 이동 가능한 공간, 목표, 블록을 즉시 구별할 수 있어야 한다. 종이·책 테마를 사용해도 되지만, 작은 화면에서 글자나 복잡한 텍스처가 문양을 가리지 않게 한다. 2×2 블록은 면적 차이가 분명해야 한다. 목표의 테두리와 문양은 블록이 접근해도 읽을 수 있어야 한다.

3D 메시·실시간 그림자·안개·Bloom은 기본 요구 사항이 아니다. 정적 벽은 미리 구성하고, 매 프레임 오브젝트 생성·파일 저장·BFS 탐색을 수행하지 않는다. 스프라이트와 UI 재질을 공유하고 반복되는 시각 효과는 필요한 범위에서 재사용한다. 보드 렌더러를 매번 생성하는 대신 레벨 전환 때 정리·재구성한다.

모바일 성능 기본 목표는 지원 대상으로 정한 실제 기기에서 안정적인 60fps다. 저성능 기기의 30fps 동작도 검증하고, 프레임 수가 바뀌어도 논리 결과와 초 단위 이동 시간이 달라지지 않게 한다. 이는 개발 목표이며 현재 달성된 성능 수치가 아니다.

앱이 비활성화되거나 정지한 동안 불필요한 애니메이션과 입력 처리를 멈춘다. 장시간 플레이에서 발열·메모리 증가·배터리 소모를 확인한다. 설치 크기는 포함한 텍스처·음원·폰트·플랫폼별 빌드로 측정하며, 원본 3D 게임의 빌드 크기를 목표로 가져오지 않는다. 현재 16개 레벨 규모에는 코어 계산보다 표시·리소스·UI 비용부터 측정한다.

## 11. 원본에서 가져올 것과 제외할 것

가져올 핵심은 격자 규칙, 블록과 목적지의 대응, 동시 조작, 크기별 통로 차이, Undo·Reset 의미, 16개 레벨 데이터다. 동봉 Python 코드를 읽고 같은 순수 이동 함수를 C# 등 대상 언어로 구현한다. Python 런타임을 모바일 앱에 포함할 필요는 없다.

원본 저장소의 `GravityPagePuzzle.cs`와 `PuzzleBase.cs`는 동작 참고 자료다. `GravityPagePresentation.cs`, `GravityPageControl.cs`, `GravityPageRailPhysics.cs`는 방·UI·물리·문 연출에 결합되어 있으므로 새 2D 코어로 그대로 복사하지 않는다. 현재 보정 코드는 레이어와 `고정 선반` 오브젝트 이름에도 의존한다.

원본의 `InGame.unity`, 씬 개편 도구 `GravityPageMigration`, 플레이어·스토리·방 시스템, 3D 생성 아트, 조명 데이터, Library, 기존 빌드는 필요하지 않다. 원본 전체 Packages 설정도 복사하지 않고 새 2D 프로젝트에 필요한 패키지만 선택한다.

기존 3D 코드에는 벽 밀착 상태에서 감속하는 미해결 문제가 있다. 실제 플레이 모드의 추가 검사에서 완전 밀착한 한쪽·양쪽 벽 조건 8개가 실패했다. 이 사실은 원본 물리 코드의 한계이며, 새로운 2D 게임이 이미 수정·검증되었다는 뜻은 아니다. 새 프로젝트는 물리 접촉과 무관한 격자 이동을 구현하고 다음 절의 실제 모바일 검사를 통과해야 한다.

## 12. 개발 순서

1. 빈 2D 프로젝트에서 F0의 벽·블록·목표와 네 방향 버튼을 표시한다. 세 명령 결과가 9절과 일치하는지 확인한다.
2. 순수 이동 함수와 목표 판정을 구현하고 동봉 16개 route를 재생해 검증한다.
3. 공통 시간 기반 이동 표현, 입력 잠금, 이동 중 Undo·Reset을 구현한다.
4. 1B·1C·1E로 복수 블록, 2×2 블록, 세 블록 조합을 검증한다.
5. 세로 화면·안전 영역·다른 종횡비·큰 글자·다중 터치 검사를 추가한다.
6. 일시정지·백그라운드 복귀·강제 종료 복구·로컬 저장을 구현한다.
7. 레벨 선택·완료 화면·설정·튜토리얼을 연결한다.
8. 실제 기기에서 기능·사용성·성능을 확인한 뒤 아트와 효과를 다듬는다.

새 레벨은 벽과 시작 배치를 만들고 BFS로 목표 도달 가능성과 경로를 검사한다. 상태 키는 블록 순서를 유지한 위치 튜플이며 방향 명령 비용은 1이다. 탐색 한도를 넘으면 미검증으로 표시한다. 대표 경로와 다른 입력열로 목표에 도착해도 정상 완료되어야 한다.

## 13. 모바일 인수 검사

### 규칙과 이동

- F0와 동봉 16개 route가 모두 각자의 목표에 도달한다. 목적지에 다른 블록을 넣어서는 완료되지 않는다.
- 2×2 블록은 1셀 폭 통로를 통과하지 못하고, 모든 블록은 벽·경계·다른 블록을 건너뛰지 않는다.
- 자유 공간, 한쪽 벽, 양쪽 벽, 타일 경계, 다른 블록 옆에서 같은 거리·시간의 이동이 같은 속도로 표현된다. 정면 벽에서는 정확히 멈춘다.
- 네 방향, 두 블록 크기, 여유 간격이 없는 표시 상태와 작은 틈이 있는 표시 상태를 검사한다. Sprite 사이의 틈을 바꿔도 논리 결과는 같다.
- 먼저 도착한 블록이 다른 블록을 조기 정지시키지 않는다. 다음 명령에서는 도착한 블록도 움직인다.
- 30/60fps, 큰 deltaTime, 서로 다른 해상도에서 논리 결과와 이동 시간이 같다. 목표점을 넘어가거나 블록끼리 통과하는 표현이 없다.

### 터치와 화면

- 한 터치로 한 명령만 실행한다. 길게 누르기·빠른 연타·다중 터치가 명령을 중복시키지 않는다.
- 이동 중 방향 입력은 저장되지 않는다. 버튼 밖에서 손을 떼거나 앱이 비활성화되면 진행 중 입력이 취소된다.
- Undo·Reset은 이동 중에도 가능하고 오래된 애니메이션 콜백으로 위치가 다시 바뀌지 않는다.
- 작은 세로 화면, 긴 화면, 안전 영역이 큰 화면, 큰 글자 설정에서 보드와 모든 버튼이 잘리지 않는다.
- 문양과 상태를 색만으로 구분하지 않는다. 효과음·진동을 꺼도 완료와 입력 수락을 알 수 있다.

### 저장과 앱 생명주기

- 이동 중 일시정지 후 오래 기다려도 위치가 변하지 않는다. 복귀 후 누적 시간으로 블록이 순간 이동하지 않는다.
- 이동 중 앱 전환·화면 잠금·포커스 상실·프로세스 종료를 각각 검사한다.
- 프로세스 재시작 시 마지막 확정 상태와 이동 횟수·방향·Undo 기록이 일치한다. 완료 기록은 중복되거나 사라지지 않는다.
- 저장 중 중단, 손상된 파일, 레벨 데이터 버전 변경을 처리해 다시 실행 가능한 상태로 복구한다.
- 레벨 전환을 반복해도 오브젝트·이벤트 구독·메모리가 누적되지 않는다.

### 실기기 확인

에디터에서 화면 비율을 바꿔 보는 검사와 실제 휴대폰 검사를 구분한다. 지원할 Android/iOS 기기에서 한 손 조작, 작은 목표의 가독성, 백그라운드 복귀, 프레임 안정성, 장시간 발열을 확인한다. 키보드로 테스트를 통과했다고 터치 사용성이 검증된 것은 아니다. 최단 경로 증명과 초행 플레이의 재미도 별도로 평가한다.

## 14. 동봉 데이터 검사 실행

Python 3.10 이상에서 이 폴더를 열고 실행한다. 이 명령은 개발 중 데이터 검증용이며 모바일 앱의 실행 절차가 아니다.

```sh
python verify_layouts.py
python verify_layouts.py --shortest
```

첫 명령은 데이터 유효성과 대표 경로를 검사한다. 두 번째는 BFS로 더 짧은 경로가 없는지도 확인한다. 기본 상태 수 제한은 레벨당 40,000개이고 한도에 도달하면 오류로 종료한다. JSON을 수정하거나 레벨을 재생성하지 않는다. 현재 동봉 16개 레벨은 이 격자 검사를 통과했지만 새 2D 앱의 화면·입력·성능은 구현 후 별도 검증이 필요하다.

## 15. 모바일 구현 인계용 지시문

> 이 문서와 layouts.json을 기준으로 세로 화면의 2D 스마트폰 중력 퍼즐을 구현한다. 기본 조작은 네 방향 터치 버튼이며 개별 블록 드래그·기기 기울이기·이동 중 방향 변경은 사용하지 않는다. 정수 격자에서 정지 위치를 계산하고 스프라이트로 동시에 표현한다. Rigidbody2D 접촉을 정답이나 속도의 기준으로 사용하지 않는다. 블록마다 자기 목적지가 있고 모두 도착한 뒤 이동이 끝나야 완료한다. 한쪽·양쪽 벽 옆에서도 감속하지 않게 한다. 이동 중 Undo·Reset, 다중 터치 차단, 안전 영역과 종횡비 대응, 일시정지·백그라운드 복귀·마지막 확정 상태 저장을 구현한다. 원본 BookTower의 3D 씬·캐릭터·방·스토리에는 의존하지 않는다. F0부터 시작해 16개 격자 경로를 검증하고, 실제 휴대폰의 터치·저장 복구·성능 검사를 별도로 보고한다.
